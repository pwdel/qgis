# Trail elevation profiles — 2026-10-09

The three page-ready SVGs in `derived/profiles/` cover every named State trail intersecting its sheet footprint with `HorseAllowed=Yes`: ranch 3 names / 3 continuous sections; Mount Carmel 2 / 2; Red Canyon 22 canonical names / 43 continuous sections. These are terrain-model profiles along mapped lines, not surveyed tread profiles or current permission. Arches Trail has contradictory published fields (HorseAllowed=Yes and Hiking Only); its chart is marked USE CONFLICT.

The complete intersecting named inventory includes State and USFS records, raw names, IDs, horse-use/restriction fields and selection reasons. Blank USFS saddle fields remain unknown. Cassidy has an explicit USFS saddle-management field but State geometry already represents the name, so a second overlapping profile is not added. Unnamed paths and named records lacking affirmative horse evidence are retained outside the selected profile inventory where applicable; no route is manufactured from a ranch route list.

Aliases `Casto` → `Casto Canyon`, `Rich` → `Rich Trail`, `Cassidy Trail` → `Cassidy` group names for display only; raw names and IDs remain in inventory. These are editorial name groupings, not proof that disconnected portions form a ride. Geometries are projected to EPSG:26912, intersected with the existing editorial footprint, unioned and merged only through touching degree-two endpoints. Branches and disconnections remain separate sections. No endpoint snapping, straight connectors or gap-spanning ascent is used. An asterisk marks a component endpoint clipped at the map boundary; a full published route may extend beyond this map. Each component's start is the westernmost endpoint (southern endpoint if equal easting); closed loops retain source start. Map cutouts show only local route geometry, north up, with colored start dots and component numbers. They are orientation sketches, not navigation maps or topographic basemaps.

## DEM and numeric method

Profiles uniformly use the existing USGS 3DEP ImageServer mosaic for each area: approximately 15m, 10m and 13.75m output pixels. This is output spacing; native source resolution and per-pixel lidar provenance remain unverified. No native one-meter accuracy is claimed. The existing Thunder native 1m crop covers only part of the region. `sources/profiles/native-dem-discovery.json` records a broader USGS one-meter catalog search: 187 candidate tile records (about 33.2GB total advertised bytes, including potentially overlapping products). It is discovery evidence, not a route-specific coverage audit; complete native tiles were not acquired or validated. The mosaic fallback is therefore explicit and consistent, with no mixed-resolution seam inside a profile.

Sampling uses equal intervals no longer than 30m (or twice output pixel width, whichever is larger), includes exact endpoints and uses bilinear interpolation only when all four source cells are valid. Nodata is retained in CSV and breaks plotted lines. Distances follow source polyline geometry, not road odometers or rounded publisher miles. All elevation units are meters before conversion to feet; X is miles from component start. Y is elevation relative to that component's chosen start. If its start sample is missing, metadata explicitly identifies the first valid sample as zero. No elevation offset is transferred between components.

A three-sample median followed by a three-sample moving mean reduces cell-scale noise; each contiguous valid run retains its original endpoints. The nominal three-sample window spans approximately 60m between outer samples at the maximum sampling step. Accumulated ascent/descent uses turning points with a 3m reversal threshold. Sub-threshold oscillations and final incomplete reversals are suppressed; totals are approximate and can differ from net endpoint change. This threshold is a noise rule, not estimated DEM accuracy. Totals are computed independently within valid runs; no vertical jump across a gap is counted. A zero total may reflect a very short segment or suppressed variation, not level tread. Components shorter than two output pixels are flagged in JSON. Terrain cells and generalized trail positions cannot resolve narrow benches, exact cliffs, switchback tread, overhangs or current conditions.

The dense Red Canyon page shows all 22 names. Component colors/IDs link chart lines, orientation cutouts and separate distance/ascent/descent annotations. Disconnected pieces each start at distance/elevation zero, and no combined continuous-route total is presented. Axes share unit meanings but have independent ranges. Text is 7–8pt at the intended 414mm-wide placement. Ranch and Mount Carmel use larger cards. Page PNGs are QA companions.

## Data schema and reproduction

`profiles.json` is the combined register; `{area}-profiles.json` contains `area`, `dem_source`, `dem_output_pixel_m`, `native_resolution_verified`, `profiles`, `inventory`, `page_profile_ids`, `omitted_page_components`, `plot_svg`, `named_route_count`, and `summary`. Each profile includes ID, label/name, component counts, map-clipping flag, original State source IDs, horse status, start/end WGS84 coordinates, direction, distance, ascent/descent, DEM provenance, actual sample spacing, nodata counts, short-component flag and CSV path. `{area}-routes.geojson` stores each selected component in WGS84 with the same metadata. Each CSV provides distance miles, raw and smoothed elevations in meters, relative feet and validity.

Run `python3 scripts/test_trail_profiles.py` and `python3 scripts/trail_profiles.py` in the documented QGIS/GDAL/NumPy/Matplotlib environment. Analytic tests cover known rise/fall, noisy level ground, nodata gaps, preserved endpoints and isolated samples. Generation uses saved source snapshots and does not refresh external evidence. All three SVG/PNG pages were rendered and the dense page visually checked for overlap; full atlas print QA remains a separate assembly check.
